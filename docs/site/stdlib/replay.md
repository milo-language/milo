# std/replay

The record/replay engine behind `MILO_RECORD` and `MILO_REPLAY`. Run a program with
`MILO_RECORD=trace.mrr` and every nondeterministic input it reads (clock, entropy,
environment, files, sockets, subprocesses, the green scheduler's order, extern calls, OS
thread ordering) is appended to the trace; run it again with `MILO_REPLAY=trace.mrr` and
each of those inputs is answered from the trace instead, so the run repeats exactly.
`milo trace trace.mrr` lists the records.

Programs do not call this module to get that: std's own IO, time, random and process
functions are already hooked, and the compiler routes extern calls through generated
recording wrappers. The functions here are the hook API those use, for a library that
wraps a new source of input itself.

```milo
from "std/replay" import { replayOff, replayRet }
```

## Example

A hooked call: one compare when neither variable is set, recorded or answered from the
trace otherwise.

```milo
from "std/replay" import { replayOff, replayRet }

extern fn sensorRead(): i64

fn readSensor(): i64 {
    if replayOff() {
        unsafe { return sensorRead() }
    }
    return replayRet("sensor.read", "", false, (): i64 => {
        unsafe { return sensorRead() }
    })
}
```

See [Record and replay](https://github.com/milo-language/milo/blob/main/docs/record-replay.md)
for what is captured, the trace format, holes and divergence.

### `ReplayLock`

```milo
pub struct ReplayLock
```

The one lock around the trace. A spin lock with a sleep, not a pthread mutex: it has
to work before any initializer has run (a hook can fire from another module's global
initializer), and the critical sections are a record's worth of work. Reentrant per
thread, so a divergence reported while it is held can still run the exit hook.
`@synchronized` tells the checker's thread pass that the shared state above, written
only inside `run`, is not racing.

#### `ReplayLock.run`

```milo
fn ReplayLock.run(self: &ReplayLock, f: () => void): void
```

Run `f` holding the record/replay engine's lock; re-entrant on the same thread.

### Functions

#### `miloReplayStart`

```milo
pub fn miloReplayStart(argv: *u8): void
```

Called first thing in main, before any global initializer: decides record/replay (so
an initializer's allocations already come from the fixed heap) and restarts with ASLR
off when needed, which must happen before the trace is opened.

Only the restart and the heap happen here: the rest of the decision waits for
std/replay's own initializer, because its state (the trace window, the fd tables) is
set up by the global initializers that run after this.

#### `miloReplayStop`

```milo
pub fn miloReplayStop(seq: i64): void
```

The function a debugger breaks on to stop a replay at a chosen record: with
MILO_REPLAY_STOP=&lt;N>, replay calls it right after consuming record N, so the
replaying program is stopped with record N's call just answered. External linkage
keeps the symbol (`b miloReplayStop`); it then raises SIGTRAP, so a debugger
attached without a breakpoint stops here too. With MILO_REPLAY_STOP_PRINT=1 it
prints instead and the replay continues (for tests and a UI that only wants the
position).

#### `replaySyncAtomic`

```milo
pub fn replaySyncAtomic(op: &string, f: () => i64): i64
```

One ordered atomic operation (std/sync's Atomic* types): `f` performs it and returns
its result. Recording runs it inside the trace lock, so the record order is the order
the operations really happened in; replay runs it on this thread's turn and checks it
returned what it returned when recorded.

#### `replaySyncEnter`

```milo

```

Replay: wait until this thread's next record is at the head of the trace. std/sync
calls it before taking a primitive's own lock, so the operation runs exactly when it
ran in the recording, after every operation recorded before it. No-op when recording.

#### `replaySyncNote`

```milo

```

One ordered sync operation, made while the primitive's lock is held: what it did
(`op`, e.g. "recv") and how it came out (`outcome`: ready or not, the value an atomic
returned). Recorded as `sync.<op>` with both in the arg; under replay the same
operation must come out the same way, or the run has diverged.

#### `replayWrite`

```milo
pub fn replayWrite(fd: i32, buf: *u8, len: i64, socket: bool): i64
```

One write(2) or send through the trace: what is recorded is that it happened, to
which fd, how many bytes were offered and how many went (or the errno). Under replay
the write reaches the OS only for the inherited stdout and stderr, so the user sees
the program's output; a write to a file, socket, pipe or pty is answered from the
trace and never performed (the peer does not exist, and a replay must not change
the filesystem).
