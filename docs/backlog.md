# Backlog — prioritized

A **do-next ordering** across the open work. Status source of truth is [roadmap.md](roadmap.md); this file only ranks by return-on-investment vs effort. `Ref` links the canonical entry.

**Refs name things, never line numbers.** Every `roadmap.md:NNN` in here had rotted — `:115` pointed at an unrelated shipped item, `:109`/`:123` at blank lines. A ref that silently points somewhere plausible is worse than none. Same for `#N` cross-references: renumbering after a deletion left one item pointing at itself and another at a deleted entry, so prefer naming the item.

**Verify before working an entry.** These are written from intent and rot as code lands: three entries here (LSP rename, `milo doc`, the parser bug's diagnosis) turned out already shipped or misdiagnosed, and two more (iterators' "needs associated types", Option's "needs closures") named blockers that no longer existed. The full audit then found three more shipped entries still listed (SIGWINCH select arm, shuf/Promise ergonomics, benchmarking harness). Check the code first; correct the entry when it lies.

**Open stdlib items live in this file too**, tiered the same way as the compiler/language work.

**Shipped items are deleted from this file, not struck through** — git history and roadmap.md keep the record. If an entry ships but leaves real work behind, only the leftover survives here, rewritten as its own item.

No handle scheme catches that. The rule that would is *an unrooted heap value may not be live across any call that can collect*, i.e. `pushTemp` becomes an API rule rather than a convention. **Rust punts this to `unsafe` in every GC crate that has tried, and Milo starts from a better position — worth checking before assuming it inherits the difficulty.** Three pieces already exist and none of them is a new type system: **(a) second-class refs** mean a raw `&T` into the heap cannot be stored or returned at all, so the only values that can be live across a call are owned ones and indices — a much smaller surface than Rust's, where any `&'a T` can be threaded anywhere a lifetime permits. **(b) The poison mechanism is built.** `freezeViewSource` marks a binding borrowed with PATH granularity and `errorIfFrozen` rejects conflicting uses while it is live; a view of `r.items()` blocks writes to `r.data` and nothing else. "Invalid after a safepoint" is that same per-binding flag with a different trigger. **(c) The trigger is one bit, not an effect system.** Effect rows and capabilities were rejected for Milo (`docs/effects-and-capabilities.md`) and this does not need them: "can this callee collect?" is a single boolean computed by transitive reachability from whatever calls `collect()`, which is exactly the shape `retainsParam` already computes by walking callee bodies, and Milo compiles whole-program in one process against a flat namespace so the closure is a graph walk over HIR that exists (the same reason Tier 2 #20 is easier here than hawk was for Rust). **What is genuinely unresolved and must be decided first:** how the rule is stated at a boundary. `retainsParam` gets to fail closed because over-rejecting a closure is an inconvenience; over-rejecting "may collect" would poison every value across every call in an interpreter, which is unusable. So this needs the opposite default — an explicit marker on the collecting functions, propagated — and the cost of getting that wrong is a false proof of rootedness, not a false alarm. Do not start it as an inference pass. | `src/checker.ts` (`freezeViewSource`/`errorIfFrozen`, `retainsParam`), `docs/effects-and-capabilities.md`, milojs `docs/milojs-arena-safety.md` step 5 |
| 24 | **Combinator fusion — worth ~1.3x on a chain, and the premise usually given for it is FALSE** | L-M | M | **MEASURED 2026-08-17, prompted by an outside review claiming "eager map/filter means idiomatic code allocates per stage, so hot paths regress to while-loops".** That claim does not hold here, and the opposite does. On 1M i64, four consecutive runs of one program (cross-program numbers are useless — the same `map` measured 4270us in one binary and 1300us in another, so only variants timed together in a single run are comparable): **`v.map(f)` 1180-1333us, a hand-written `for-in` + `reserve` with the arithmetic INLINE 1729-1925us, the same loop calling a closure 2011-2230us.** The builtin beats hand-rolled code including the version with no call at all, so "the pretty version regresses to a while-loop" is backwards — the while loop is the slow one. Two reasons: `genVecMap` already emits ONE exact-size `malloc(len * elemSize)` (there is no per-stage growth realloc to eliminate for a single stage), and an indexed `v[i]` loop pays a bounds check the builtin's pointer walk does not. **What IS real is the CHAIN**: `filter().map()` builds and frees an intermediate buffer and walks the data twice. Against a hand-fused single-pass loop over 2M: 15335/7586/6394us chained vs 7911/6173/4664us fused (the first run of each is cold; warm ratio is **~1.3-1.4x**). So a pass that recognises adjacent `VecFilter`/`VecMap` in HIR and emits one loop is worth about a third on multi-stage chains and NOTHING on single stages. Decide with that number, not the premise: it is a real but modest win, on a shape (2+ stage chains on large vectors) that has to be shown to be hot before it earns a compiler pass. Related and NOT the same thing: lazy/fusing ADAPTERS are declined outright (Tier 2 #6) because laziness pays only through aggressive inlining and drags associated types into the trait system; this entry is the compiler-pass alternative, which needs neither. | `src/codegen.ts genVecMap`/`genVecFilter`, `src/lower.ts`, Tier 2 #6 |

## Language ergonomics: `for (i, x) in vec` tuple binding

for-in binds a single name, so index+element loops stay C-style `while i < len()`.
Add tuple/destructuring binding: `for (i, x) in vec.enumerate()` (`.enumerate()`
already exists). Converts most `while i < .len()` loops to for-in. match already
destructures tuples, so the pattern machinery exists. Scope: parser + checker +
codegen bind the pattern per iteration.
